# 1. 프로젝트 목적이 문제 지도에서 실제로 도출되는가

## 1.1 "완료 6조건"의 원문 추적성부터 끊겨 있다

허용된 범위에는 이름 붙은 "완료 6조건" 또는 "신뢰 6조건"의 여섯 항목이 열거돼 있지 않다. FOUNDING-IDEA §3의 G-A 설명에서 "신뢰 6조건"이라는 명칭만 나오고 내용은 없다.

따라서 정확한 공식 목록과 문제 지도의 일대일 대응은 이 원문만으로 재감사할 수 없다. 이는 그 자체로 창립 목적의 추적성 결함이다.

이 검수에서는 요청 취지에 맞춰 FOUNDING-IDEA §1 한 문장을 독립적으로 검증 가능한 여섯 약속으로 분해했다.

## 1.2 여섯 약속별 도출성

| §1의 약속 | 뒷받침하는 문제 | 판정 |
|---|---|---|
| 1. 엔지니어링을 모르는 사람이 **아이디어만 가지고 시작**할 수 있다 | P1, P24, 일부 P6 | **부분** |
| 2. 에이전트가 **현업 개발 프로세스를 대신 밟는다** | P6·P7, P21a·P21b, 일부 P24 | **부분** |
| 3. **정말 필요한 판단만** 사용자에게 올린다 | P14, P31, P35가 일부 인접 | **실질 미도출** |
| 4. 사용자가 **답할 수 있는 말로** 묻는다 | P13, P23, P28, 일부 W2 | **부분** |
| 5. "다 됐다"는 말을 **실행된 검사와 증거에 결합**한다 | P5, P25, P26, P29, P30, P39 | **가장 강하게 도출되나 여전히 불완전** |
| 6. 되돌릴 수 있는 것은 되돌리고, 되돌릴 수 없는 것은 **미리 멈춘다** | P22, P33, 일부 P21a·P31·P35 | **핵심 문제 누락** |

### 1) 아이디어만 가지고 시작

P1은 명확하지 않은 상태로 빌드에 들어가 중간에 엎는 경험을 제공하고, P24는 무엇을 완주로 볼지 정해야 한다고 말한다. 이 둘은 "아이디어만 있는 상태를 구조화해야 한다"는 필요를 어느 정도 지지한다.

그러나 P1은 여전히 다음 셋을 한 항목에 섞는다.

- 관찰: 중간에 프로젝트를 엎는다.
- 원인 가설: 시작 시 방향을 충분히 명확히 하지 않았다.
- 해법: 정한 것을 내내 살아 있는 기준으로 유지한다.

이전 반려가 지적한 "정당한 피벗까지 실패로 취급할 위험"은 P27을 별도 항목으로 추가했을 뿐 P1 자체에서는 해소되지 않았다. P1이 관찰에서 곧바로 특정 원인과 특정 해법을 확정하므로, 약속 1은 부분적으로만 도출된다.

### 2) 현업 개발 프로세스를 대신 밟음

P6은 이 약속의 직접 근거처럼 보인다. 하지만 P6 원문은 사용자 문제인 "어떤 절차가 필요한지 모른다"와 해법인 "리서치로 표준을 찾아 에이전트가 따르게 한다"를 결합한다. "보편 표준 하나"를 "공통 최소 바닥 + 유형별 + 위험별"로 고친 것은 개선이지만, 그 조합이 실제로 적합한 절차라는 근거는 여전히 없다.

또한 P21b는 일부 단계는 에이전트가 대신할 수 없고 사람이 해야 한다고 말한다. 따라서 "대신 밟는다"를 모든 수행의 위임으로 읽으면 P21b와 충돌한다. "에이전트가 전체 과정을 조율하되 사용자 권한이 필요한 단계는 안내한다"는 뜻이라면 §1 문장을 그렇게 좁혀야 한다.

현재 상태에서는 사용자에게 적합한 절차를 **선택하는 문제**와 절차를 **강제하는 해법**이 구분되지 않았다.

### 3) 정말 필요한 판단만 묻기

이 약속은 여전히 문제 지도에서 나오지 않는다.

P14는 결정 지점이 이미 정확하게 발견됐다고 가정하고 선택지·근거·위험·불확실성을 어떻게 보여줄지를 다룬다. P31은 자동화가 중단되거나 전문가에게 넘어가야 하는 극단 경계를 다룬다. 어느 항목도 다음 오류를 문제로 정의하지 않는다.

- 사용자가 정해야 할 사안을 에이전트가 임의로 처리하는 거짓 음성
- 에이전트 재량으로 처리할 사소한 일을 계속 사용자에게 묻는 거짓 양성
- 사용자·에이전트·전문가 중 누가 결정권자인지 잘못 라우팅하는 오류
- 위험이 어느 수준일 때 판단 회부가 필요한지 잘못 분류하는 오류

이전 검수의 동일한 지적은 P24~P39 중 어느 항목으로도 온전히 채택되지 않았다. P31은 전문가 이관이라는 한 경계만 다룬다.

따라서 §1의 "정말 필요한 순간만"은 현재도 문제 근거 없는 제품 약속이다.

### 4) 사용자가 답할 수 있는 말로 묻기

P13, P23, P28이 축을 형성하므로 문제 지도 차원의 방향은 생겼다.

하지만 PRD에서 P13의 요구사항은 goppi 자체의 유한한 사용자 대면 문자열만 포함하고 에이전트 대화 전체를 명시적으로 제외한다. P13이 관찰된 표면은 반복적인 대화와 설명인데, 요구사항은 그 표면을 제외한다. 이전 검수에서 지적한 추적성 단절이 그대로다.

또한 짧은 문장·쉬운 용어·스크린샷은 이해를 보장하지 않는다. P28이 이해 검증 공백을 채택했지만 요구사항과 시험이 모두 `ORPHAN`이다. P14의 "되묻는 비율"도 이해나 판단 품질을 측정하지 않는다.

따라서 문제 지도에는 관련 항목이 생겼지만, 목적 문장이 약속하는 "답할 수 있는 상태"까지는 도출되지 않는다.

### 5) 완료 주장과 실행된 검사 결합

여섯 축 중 가장 잘 보강됐다.

- P5: 완료 주장과 실행된 검사 결합
- P25: 검사 독립성·이해충돌
- P26: 검사되지 않은 범위
- P29: 상충 판정
- P30: 환경 재현성
- P39: 증거 경로 조작 위험

이 조합은 이전 검수에서 가장 위험하다고 본 공백 네 개를 목록에는 올렸다.

그러나 다음 공백은 남는다.

- 검사 파일이 변조되지 않았다는 사실과 검사가 **올바른 주장을 검사한다는 사실**은 다르다.
- 무엇이 검사되지 않았는지 표시하는 것과 **필요한 검사가 빠지지 않았다는 것**은 다르다.
- 실제 환경에서 실행하는 것과 검사 결과가 **사용자의 인수기준·버전·산출물에 의미상 대응한다는 것**은 다르다.
- 화면이나 녹화는 판독을 돕지만 기계 판정의 정확성을 높이지 않는다.

즉 실행 사실·독립성·환경은 다루기 시작했지만, 검사와 완료 주장의 **의미 적합성**은 독립 문제로 서지 않았다.

### 6) 되돌리거나 미리 멈춤

P22는 반복 수정 실패 후 전략 전환을, P33은 git 밖 상태를, PRD의 3분류는 reversible/compensatable/irreversible 처리를 제시한다.

그러나 문제 지도에는 다음 사용자 문제가 없다.

> 비엔지니어는 어떤 행위가 실제로 되돌릴 수 있는지, 보상만 가능한지, 불가역인지 판단할 수 없고, 잘못 분류된 복구 약속을 검증할 수 없다.

PRD의 3분류는 문제에서 도출된 요구사항이 아니라 곧바로 설계 규칙으로 등장한다. P22의 "롤백·재시작 선택지"는 반복 수정 실패를 다루며, 결제·발송·DNS·데이터 손실 같은 행위의 복구 가능성 판정과 다르다. P33도 "git으로 안 돌아온다"는 범위만 말할 뿐, 복구 가능성의 사전 판정과 복구 성공 검증을 다루지 않는다.

따라서 §1 마지막 약속도 문제 지도에서 충분히 도출되지 않는다.

### 목적을 확장하거나 완료 정의와 충돌하는 항목

| 항목 | 판정 |
|---|---|
| P32 | "사용자가 원한 것" 확인과 "최종 시장 사용자 가치 검증"은 다르다. 후자는 제품 발견·시장 검증이라는 별도 범위를 만든다 |
| P34 | P24는 인터넷 공개까지를 완주로 정했는데 P34는 공개 순간에 운영 책임이 없으면 미완성이라고 말한다. 둘 중 완료 정의가 무엇인지 결정되지 않았다 |
| P7 | GitHub 표준은 P6 또는 G-A에 간접 연결될 뿐, 배포 웹 앱 완주에 항상 필요한 독립 사용자 문제는 아니다 |

W2는 P2·P13 및 PRD 한 줄의 "무슨 일이 일어났는지 알아본다"에 연결된다. 따라서 단순 꾸미기로 강등하면 오히려 목적 연결이 끊긴다. W1도 유료 자원 결정을 받는 PRD §2.1과 연결되므로 "아무 조건 없이 optional decoration"이라고 보기 어렵다.

## 1.4 문제가 뒷받침하지 않는 목적 문장

명확하게 남은 미지지 목적 문장은 다음과 같다.

1. **"판단이 정말 필요한 순간만"** — 판단 지점 탐지·권한 라우팅의 정확도 문제가 없다.
2. **"되돌릴 수 없는 것은 미리 멈추게"** — 복구 가능성 분류 오류와 사전 영향 판단 문제가 없다. PRD의 3분류는 문제 근거 없이 제시된 해법이다.
3. **"에이전트가 현업 개발 프로세스를 그 사람 대신 밟게"** — 올바른 프로세스 선택·적합성 검증 문제가 없고, P21b와 문언상 긴장이 있다.
4. **"그 사람이 답할 수 있는 말"의 강한 의미** — P13은 문장 난이도, P23은 형식, P28은 미해결 문제일 뿐이다. 의미·불확실성·결과를 이해한 결정이라는 완료 조건은 아직 없다.
5. **"엔지니어링을 모르는 사람" 일반화** — 실제 근거는 주로 한 소유자이며, P24~P39는 검수자 추론이다. 첫 제품 시나리오를 좁힌 것은 프로젝트 유형을 좁힌 것이지 사용자 능력 세그먼트를 검증한 것이 아니다.

추가로 PRD 한 줄은 FOUNDING §1의 판단 라우팅과 복구 약속을 삭제했다. 따라서 프로젝트 최상위 목적이 FOUNDING과 PRD에서 서로 다른 폭으로 존재한다.

# 2. 5층 배치 오류

## 2.1 구조 자체의 오류

### 층 1 "무조건 해결"과 범위 딱지가 충돌한다

층 1은 "사용자가 겪는 아픔 — 무조건 해결"로 정의되지만 다음 항목이 같은 층에서 🔜·◐ 또는 릴리스 미정으로 표기된다.

- P7, P8, P21b, P36, P37, P38
- PRD상 P28, P31, P32, P36~P38은 릴리스가 `❓`
- P24, P26~P38 상당수는 요구사항·시험 모두 `ORPHAN`

문제가 존재하는 것과 현재 제품이 해결하기로 약속한 것은 다른 축이다. 층 1을 "채택된 사용자 문제"로 정의할 것인지, "현재 제품이 무조건 해결할 문제"로 정의할 것인지 하나를 골라야 한다.

### 항목 수와 행 의미가 맞지 않는다

초안은 층 1을 "기존 12 + 신규 16"이라고 한다. 그러나 같은 문서의 기존 항목 표에는 P7과 P21a·P21b를 각각 세면 14행이 있고, 신규 16건까지 합하면 30행이다.

PRD에도 층 1 행이 30개다. P7을 P6 하위로 보고 P3을 폐기 흔적으로만 본다면 독립 문제 수는 다시 달라진다. 이는 단순 산수 문제가 아니라 "문제 하나에 한 행"이라는 규칙이 무엇을 문제 단위로 세는지 아직 정의되지 않았다는 뜻이다.

### 5층에는 해법 가설을 놓을 자리가 없다

이전 검수는 P11·P12를 "문제"가 아니라 "해법 가설"로 분류했다. 재구성은 둘을 "개선·희망"에 넣었다. 하지만 해법 가설과 optional decoration은 다르다.

- P12는 P2·P13·P23을 푸는 후보 해법이다.
- P11은 사용자 문제 없이 제안된 기능 아이디어다.

둘을 같은 층에 넣으면 다시 문제–해법 추적성이 끊긴다. 해법은 독립 P 번호가 아니라 해결하려는 문제 아래 후보로 연결하는 편이 맞다.

그러나 최종 FOUNDING은 다시 "소유자의 실제 강점은 승인이 아니라 질문"을 대표 문제 문장으로 사용하고, PRD도 "강점은 질문"을 문제 열에 쓴다.

따라서 초안에서 받아들인 재서술이 최종 지도에 반영되지 않았다.

## 3.2 이전 반려의 중요한 미반영 사항

- **P13의 실제 발생 표면**: 에이전트 대화가 실제 발생 표면인데 PRD가 그 표면을 제외한다. 미반영.
- **P14 시험**: "되묻는 비율"이 혼란을 보상할 수 있다는 지적을 주석으로만 남김. 잘못된 권고 거절 시험은 "재설계 후보"일 뿐 채택되지 않았다.
- **C1**: 차단 3분류(안전·무결성·작업흐름) 권고가 반영되지 않고 "재판정 필요" 상태. 초안의 "미결 항목 0"과 직접 충돌.
- **C2**: 이전 검수가 "P12가 해결했다고 선언할 수 없다"고 했는데 현 FOUNDING은 다시 "P12가 푼다"고 확정. 명백한 미반영.
- **C4**: 같은 크기만으로는 부족하며 기본 선택·순서·권고 문구·색·애니메이션까지 시험해야 한다는 권고 미반영.
- **P5 대응 폭**: 부분 대응 표시가 구조화되지 않았고 추적성 표에서는 전체 대응처럼 읽힌다.
- **대상 사용자 세그먼트**: 프로젝트 유형 문제만 해소됐고 사용자 능력 세그먼트 문제는 남았다.

| P26 | 높음 | 정확히 채택. 단 "알려진 미검사 항목"과 "검사가 필요한지조차 모르는 항목"을 구분해야 함 |

| P29 | 높음 | 정확히 채택. 그러나 현재는 PRD가 가진 설계 질문이지 실제 사용자 고통의 관찰은 아님 |
| P30 | 높음 | 핵심 정확. `환경 A 통과 ≠ 환경 B 재현`은 가능성이지 모든 프로젝트의 발생 사실은 아님 |

| P33 | 부분 | 이전에는 DB·클라우드·DNS·발송 메일·시크릿 폐기·웹훅이 있었으나 DNS·호스팅·DB로 축소됨. 범위 축소 흔적이 없음 |

| P35 | 문언 충실 | "과금이 공개와 함께 시작된다"는 무료 계층·후불·무과금 배포를 배제하는 과잉 일반화 |
| P36 | 의도적 축소 | 고객 데이터가 없는 첫 제품에 맞춰 자기 소스·시크릿으로 좁힌 것은 합리적. 다만 라이선스·IP 판단은 사라짐 |

| P38 | 충실 | `[MED]` 보존. 외부 소원 문구를 추가했으나 이 원문만으로 강한 소원 여부를 재감사할 수 없음 |
| P39 | 문언상 충실 | 이전 §4 권고를 정확히 옮겼지만 "속이려는 의도"를 단정한다. P25와 경계를 명확히 해야 함 |

P25와 P39의 구분은 다음처럼 정리해야 한다.

- P25: 검사 작성자·실행자·판정자의 이해충돌 및 검사 약화
- P39: 이미 생성된 증거·로그·상태 표시 경로의 변조 가능성

현재처럼 둘 다 "자기 채점/자기 증거 조작"으로 쓰면 중복이 다시 생긴다.

## 3.4 "미결 항목 0"은 사실과 양립하지 않는다

초안은 미결 항목이 0이라고 선언한다. 그러나 허용된 문서 안에서만 보아도 다음이 명시적으로 미결이다.

- C1: "재판정 필요"
- P29: "아직 답 없는 물음"
- 다수 `ORPHAN`
- P7·G-A 수용 시험 재설계 필요
- P14 시험 재설계 후보
- P4/C3 가설 단계

따라서 "처분 승인 0건 미결"과 "문제·요구사항·충돌 0건 미결"을 구분하지 않은 과장이다.

# 4. 여전히 빠진 문제

## 4.1 필요한 판단의 선별·권한 라우팅 오류

가장 중요한 잔존 누락이다.

> 에이전트 재량, 사용자 결정, 전문가 판단을 잘못 구분하면 사용자는 불필요하게 방해받거나 필요한 결정에서 배제된다.

P14는 표현, P31은 중단·전문가 이관, PRD §2.1은 이미 분류가 끝난 행위의 처리다. 판단 지점 자체를 탐지하는 문제는 없다.

필요한 시험은 단순 질문 횟수가 아니라 다음 두 오류율이다.

- 반드시 물어야 할 결정을 묻지 않은 비율
- 묻지 않아도 될 일을 사용자에게 넘긴 비율

## 4.2 복구 가능성 분류와 복구 성공 검증

> 비엔지니어는 reversible·compensatable·irreversible을 구분하기 어렵고, "복구됐다"는 주장도 판정할 수 없다.

P22는 반복 수정 전략, P33은 코드 외부 상태다. 둘 다 행위 전 복구 가능성 판정과 행위 후 복구 성공 검증을 완전히 다루지 않는다.

§1의 마지막 약속을 지탱하려면 독립 문제가 필요하다.

## 4.3 남은 위험의 의미와 심각도

FOUNDING §2는 사용자가 "남은 위험이 무엇인지 판단하지 못한다"고 직접 전제한다. 그러나 P26은 검사되지 않은 항목만 말한다.

미검사 항목과 잔여 위험은 다르다.

- 검사는 했지만 위험이 남을 수 있다.
- 위험을 발견했지만 수용하기로 할 수 있다.
- 위험의 발생 가능성·영향·복구 가능성을 이해하지 못할 수 있다.
- 검사 가능하지 않은 위험도 있다.

따라서 "남은 위험을 사용자가 판단 가능한 형태로 정리하지 못한다"는 문제가 별도로 필요하다.

## 4.4 검사와 완료 주장의 의미 적합성

P25·P26·P30·P39를 모두 해결해도 잘못된 검사를 완벽히 보호하고 재현할 수 있다.

> 실행된 검사가 실제 완료 주장·인수기준·해당 버전·해당 산출물을 의미상 검사하는지 사용자가 판정할 수 없다.

이 문제는 단순한 검사 충분성과 다르다. 검사 자체가 존재해도 엉뚱한 것을 검사할 수 있기 때문이다.

## 4.5 결정 화면의 편향과 권고 저항성

C4에서 위험을 인정하지만 독립 문제로 승격되지 않았다.

> 기본값·순서·색·권고 문구·애니메이션·누락된 대안이 사용자의 결정을 특정 방향으로 유도할 수 있고, 사용자는 그 편향을 알아채기 어렵다.

P14를 이 문제로 정확히 다시 쓰거나 별도 항목으로 만들어야 한다. "세 상태를 같은 크기로"는 해결책의 일부일 뿐이다.

## 4.6 프로젝트 유형에 맞지 않는 절차 적용

P6의 "공통 최소 바닥 + 유형별 + 위험별"은 해법 가설이다. 그 해법을 필요로 하는 문제는 다음이다.

> 프로젝트 유형·공개 범위·데이터·위험에 맞지 않는 절차와 게이트가 적용되면 필요한 검사는 빠지고 불필요한 절차는 늘어난다.

이 문제가 없으면 P6은 계속 "현업 순서가 필요하다"에서 "특정 절차를 강제한다"로 바로 건너뛴다.

# 5. 근거보다 강한 문장과 등급 정직성

## 5.1 `[검수]` 등급 판정

`[검수]`는 **문장의 출처**를 밝히는 표기로는 정직하다. FOUNDING은 P24~P39가 소유자의 직접 경험이 아니고 문장 초안도 에이전트가 썼다고 명시한다.

그러나 `[검수]`는 **증거 강도 등급**으로는 정직하지 못하다.

- 검수자 추론인지, 검수자가 확인한 외부 근거인지 구분되지 않는다.
- 소유자 채택은 우선순위 결정이지 사용자 문제 실증이 아니다.
- `[검수]`라는 이름은 독립 검증을 통과했다는 인상을 줄 수 있다.
- P24~P39를 곧바로 "모든 사용자에게 해당", "무조건 해결", 🎯로 올린 것이 표기의 주의 문구를 상쇄한다.
- P37·P38만 `[MED]`이고 나머지는 불확실성 등급이 없다. 동일하게 검수자 추론만 있는 항목 사이의 차이를 설명하지 않는다.

정직한 표기는 최소 두 축으로 갈라야 한다.

| 축 | 예시 |
|---|---|
| 출처 | 소유자 회고 / 직접 행동 관찰 / 계보 전이 / 외부 조사 / 검수자 추론 |
| 검증 상태 | 미검증 가설 / 단일 사용자 확인 / 반복 관찰 / 대상 사용자군 재현 / 반증 시험 통과 |

P24~P39는 현재 자료 기준으로 대체로 다음처럼 써야 한다.

> `[출처: 검수자 추론] [검증: H0·대상 사용자 관찰 0] [상태: 채택된 문제 가설]`

"소유자 채택"은 별도 필드로 두어야 한다.

| P38 | "소원 조사의 강한 소원" | 해당 자료가 허용 범위에서 재감사되지 않으므로 보조 주장으로만 표기 |
| P39 | 조작의 목적을 "사용자를 속이기 위해"라고 단정 | 에이전트가 증거 경로를 변경할 수 있으면 거짓 완료가 통과할 위험이 있다 |

P39의 "속인다"는 결과 위험과 행위 의도를 혼동한다. 의도적 공격, 편의상 검사 약화, 오류에 의한 덮어쓰기, 낡은 증거 재사용은 서로 다른 원인이다.

# 6. 승인 가능 상태로 만들기 위한 필수 시정

다음은 선택적 개선이 아니라 재승인의 전제다.

1. **층 1의 정의를 고친다.** "채택된 사용자 문제"인지 "현재 제품이 무조건 해결할 문제"인지 하나로 정하고, 범위·우선순위·검증 상태를 별도 축으로 둔다.
2. **모든 문제 문장을 사용자·상황·관찰 가능한 손실 형식으로 다시 쓴다.** 원인 가설과 해법은 별도 열로 분리한다. 특히 P1, P2, P6, P14, P15, P24·P25·P28·P29·P31·P33~P39가 대상이다.
3. **누락 문제를 추가한다.** 판단 지점 탐지·권한 라우팅 / 복구 가능성 분류·복구 성공 검증 / 잔여 위험 이해 / 검사와 완료 주장의 의미 적합성 / 결정 화면 편향·권고 저항성 / 프로젝트 유형별 절차 적합성
4. **P24~P39를 "채택된 미검증 가설"로 강등한다.** `[검수]`를 출처와 증거 강도의 두 축으로 분리하고 "모든 사용자에게 해당" 표현을 제거한다. P37·P38뿐 아니라 전 항목에 불확실성·반증 조건을 붙인다.
5. **이전 반려의 미해소 항목을 끝낸다.** P3 완전 폐기 또는 역사 표기로만 격리 / P13 범위에 실제 에이전트 대화 표면 포함 / P14 문제 문장과 시험 교체 / P19·P20 인과 약화 / C1 차단 3분류 / C2를 해결이 아닌 가설로 강등 / C4 편향·저항 시험 채택 / P5 부분 대응을 구조적으로 표기
6. **P24와 P34의 완료 정의 충돌을 결정한다.** "인터넷 공개가 완주"인지 "운영 가능한 상태가 완주"인지, 또는 공개 이후가 별도 제품 단계인지 명시해야 한다.
7. **FOUNDING §1과 PRD §1을 동기화한다.** 필요한 판단 선별과 복구 약속을 PRD 목적에 다시 넣거나, 실제 제품이 약속하지 않는다면 FOUNDING 문장을 좁혀야 한다.
8. **"미결 0"을 철회한다.** 처분 승인 여부와 문제 정의·요구사항·시험·충돌의 해결 여부를 분리해서 기록해야 한다.

# 종결 판정

이번 재구성은 다음 항목에서는 성공했다.

- P1+P16, P2+P17의 번호 중복을 줄였다.
- P21을 기술 안전과 사람 last-mile로 분리했다.
- P10, P19, P20, G-A를 사용자 문제 목록 밖의 별도 층으로 옮겼다.
- P22·P23의 가장 노골적인 외부 근거 과장을 축소했다.
- 이전에 빠졌던 검사 독립성·충분성·환경·상충 판정 문제를 목록에 드러냈다.

그러나 승인할 수 없는 이유가 더 근본적이다.

**문제 지도는 아직 "사용자가 겪는 문제"를 중심으로 재구성된 것이 아니라, 기존 주장·검수자 추론·해법 후보·위험 범주·장기 품질 목표를 다섯 상자에 다시 나눠 담은 상태다.** 특히 프로젝트 목적의 핵심인 판단 선별과 복구 가능성 판정은 문제 근거가 없고, 반대로 P24~P39는 대상 사용자 관찰 0건인 상태에서 "모든 사용자·무조건 해결"로 과잉 승격됐다.

따라서 판정은 **재반려**다. 파일은 변경하지 않았다.
