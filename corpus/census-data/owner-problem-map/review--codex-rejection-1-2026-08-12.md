# 1. 잘못 정의된 문제

## 1.1 §2·§2.1의 사용자와 역할 정의

### [HIGH] 대상 사용자가 하나의 검증 가능한 세그먼트로 정의되지 않았다

§2의 대상은 "소프트웨어 프로젝트를 끝까지 해본 적 없는 한 사람"이다. 그러나 이 조건은 지나치게 넓다. 로컬 자동화 스크립트 / 개인용 앱 / 사용자 데이터가 있는 공개 SaaS / 결제 서비스 / 기존 회사 저장소 / 오픈소스 배포가 모두 들어간다. P21의 RLS·개인정보·결제·환경 분리는 공개 데이터 서비스에만 강하게 적용되고, P7·G-A는 GitHub 공개 배포를 전제하며, P8은 기존 프로젝트를 전제한다. §1의 "아이디어만 주면"은 그린필드를 암시한다.

문제 집합은 한 사용자를 말하지만 실제로는 최소 세 시나리오를 섞고 있다: ① 그린필드 ② 기존 프로젝트 진단·수리 ③ 공개 서비스/오픈소스 배포. 이 셋은 완료 정의, 위험, 표준, 검증 방식이 다르다.

### [HIGH] "판정 능력이 없는 결정권자"를 가능하게 하는 중간 문제가 빠졌다

§2는 네 능력(결과·증거·잔여 위험·복구 판단)이 없다고 하고 §2.1은 사용자를 최종 결정권자로 둔다. 연결고리인 다음 질문이 문제 목록에 없다:

> 사용자가 제시된 정보의 의미·불확실성·결정 결과를 실제로 이해했는지 어떻게 아는가?

P3/P13은 설명 난이도, P14는 질문 행동, P23은 증거 형식 — 어느 것도 "이해한 뒤 내린 결정"을 정의하지 않는다. 짧은 문장, 질문, 스크린샷은 모두 이해 없는 승인을 만들 수 있다.

### [HIGH] "정말 필요한 판단"을 누가 선별하는지가 정의되지 않았다

제품 한 문장은 "판단이 정말 필요한 순간만" 묻는다고 약속하는데, 무엇이 사용자 결정인지 / 에이전트 재량인지 / 언제 위험이 충분히 커졌는지 / 언제 사람 전문가에게 넘겨야 하는지의 메타 판단 문제가 P1~P23에 없다. P14는 결정 지점이 이미 올바르게 발견됐다고 가정한 뒤 표현 방식만 다룬다.

### [MED] "사용자는 제어 대상이 아니다"가 지나치게 절대적이다

정확한 역할 원칙은: "사용자의 목표와 위험 수용 결정을 대체하지 않는다. 다만 정보 부재를 승인으로 간주하지 않고, 제품의 사실 판정은 사용자의 선호로 변경하지 않는다."

## 1.3 충돌 C1~C4

- **[HIGH] C1**: "가역이므로 차단 금지"와 "불가역만 차단"을 그대로 쓸 수 없다 — 차단 근거를 3종으로 분리해야: ① 안전 차단(피해·보상 기준) ② **무결성 차단(자기평가 이해충돌 기준)** ③ 작업 흐름 차단(오탐·지연 기준). 증거 경로 쓰기는 파일로는 가역이어도 그에 의존한 의사결정 피해는 불가역일 수 있다.
- **[HIGH] C2**: 해결 선언은 성급 — 그림의 생성·갱신·낡음·생략 비용 존재. "해결됨"이 아니라 가설.
- **[MED] C3**: 정직하게 가설로 뒀으나 P4·P6 미정의로 시험 자체가 현재 불가능.
- **[HIGH] C4**: "같은 크기" 규칙으로는 부족 — 기본 선택·순서·권고 문구·색·애니메이션도 조종한다. 필요한 시험은 "심어둔 잘못된 권고를 사용자가 거절할 수 있는가"(저항 시험). P23의 매끄러운 시각 증거는 C4 위험을 확대한다.

# 2. 빠진 문제 (전부 HIGH, 별표는 요지)

**모든 사용자에게 적용:**
1. **"완료"의 수준이 정의되지 않았다** — 프로토타입/로컬 작동/배포/공개 가능/운영/오픈소스/유지보수 가능 중 무엇이 완주인가. 이것 없이 검사·프로세스·안전 바닥·last-mile 범위를 정할 수 없다.
2. **검사 독립성·이해충돌이 명시적 P로 없다** — 자화자찬 경향·sys.exit(0)·보이는 테스트 과적합이 조사에 있는데 문제 목록에 없다. 제품 신뢰성의 전제조건.
3. **"검사되지 않은 것"을 사용자가 모른다** — 검사 통과 ≠ 충분한 검사가 존재함.
4. **정당한 요구 변경과 방향 표류가 구분되지 않았다** — 이대로면 하네스가 사용자의 학습을 "드리프트"로 막을 수 있다.
5. **사용자의 이해 여부를 검증하는 문제가 없다** — 없으면 goppi는 "잘 정리된 승인 유도기"가 될 수 있다.
6. **에이전트 "다 됐다" vs goppi "아직 모름" 충돌 처리** — PRD가 스스로 미해결로 적은 것. 왜 충돌했나·어느 증거가 빠졌나·재평가 경로가 필요.
7. **환경 차이** — "에이전트 환경에서 통과"와 "사용자 실제 환경에서 재현"의 구분.
8. **포기·중단·전문가 이관 기준** — 이 경계가 없으면 가장 위험한 프로젝트일수록 더 그럴듯한 자동 안내를 받는다.
9. **최종 사용자 가치 검증** — 기술적 인수기준을 모두 통과해도 원하지 않는 제품을 정확하게 만들 수 있다.

**프로젝트 유형에 따라 치명적:**
10. **코드 외부 상태의 복구** — DB 데이터·클라우드·DNS·발송 메일·시크릿 폐기·웹훅은 git으로 안 돌아온다.
11. **배포 후 운영 책임** — 장애 감지·백업·패치·비용 이상·개인정보 삭제·서비스 종료. "완주=공개 순간"이면 유지할 수 없는 제품을 넘겨준다.
12. **비용·계정·구독·락인.**
13. **모델에 보내는 데이터·IP 거버넌스** — 비공개 소스·고객 데이터·라이선스.
14. [MED] 도구·호스트 변화에 대한 프로젝트 이동성. 15. [MED] 사람 개발자 인계 가능성.

- **P1~P12의 [1차]가 재감사 불가** — 원문·날짜·맥락·횟수 없음. P1 해법 문장·P6 리서치·P12 이원화가 소유자 원문인지 설계 해석인지 불명.

- **P19 과잉 일반화** — 두 사례, 6가지 대안 원인.
- **P20 "7회"의 분모·목록 없음** + "안 읽음"과 6가지 다른 원인 미구분.
- **P21 "최빈 원인" 입증 안 됨** — 10%~88%는 하나의 신뢰구간이 아니라 서로 다른 표본·정의의 혼합. 방어 가능한 문장: "공개 앱에서 접근제어·설정 오류가 반복적·심각하게 관측되며 비엔지니어가 발견하기 어렵다"까지.
- **P22 타 집단 처방의 보편화** — "3사 공통 처방(롤백)"은 기록이 지지하지 않음. 방어 가능: "교정 실패 누적 시 컨텍스트·코드가 함께 악화할 수 있어 전략 전환 기준이 필요하다"까지.
- **P23 "검증 가능" 과장** — 판독 용이성 근거는 있으나 검증 정확도 근거는 없음.
- **§3.1 숫자의 출처 추적 끊김** (지정 파일 범위 내).
- **외부 조사는 "에이전트가 확인했다고 보고한 것"** — 강한 결론("최빈"·"올바른"·"3사 공통")에는 부족.

**n=1 일반화 (전부 HIGH)**: 소유자는 일반 비엔지니어보다 질문 능력·기술 노출이 높을 표본 편향 · 반증 절차(문제가 발생하지 않은 사례의 기록) 부재 · PRD의 3명 시험은 통제·비교군·완주 관찰이 없어 일반화를 보완 못 함.

# 4. 정합성 (요지)

- P5 전체 폭 vs 제품 보증 폭 불일치 — "부분 대응" 표기 또는 문제 문장 축소 필요.
- P8(기존 프로젝트)은 "아이디어만 주면"과 시작 조건이 다름 — 별도 진입 절차 없이는 같은 제품이 아님.
- P11은 핵심 약속과 무관한 기능 확장. P20은 사용자 제품 약속과 무관. G-A는 두 번째 제품.
- **제품이 하는데 문제 근거가 없는 것**: 보편 "현업 순서" 강제 · 불가역 자동 분류(구체 문제 미진술) · **증거 경로 무결성 보호(P19가 아니라 "에이전트가 자기 증거를 조작해 사용자를 속일 수 있다"라는 독립 사용자 문제로 승격해야)** · "필요한 결정만" 라우팅(정확도 문제와 시험 부재).
- **PRD 표의 구조 결함**: "문제 하나에 한 행" 규칙이 실제 표와 모순 · 다수 수용시험이 사용자 결과가 아니라 해법 존재를 검사(P13 문자열 길이 ≠ 이해, P14 되묻는 비율 ≠ 좋은 판단, P22 경로 표시 ≠ 올바른 복구 등 10건 열거).

# 5. 독립 우선순위 의견 (빌드 계획 미참조)

- **0**: 대상 시나리오·완료 수준을 먼저 결정 (그린필드 로컬 / 배포 웹 앱 / 공개 데이터 서비스 / 기존 개선 / 오픈소스 중 첫 제품 선택)
- **1**: P1+P16 — 원하는 결과·완료 기준·정당한 변경 기록 (이것 없이 P5 검사가 무엇을 검사할지 모름)
- **2**: P2+P17+P18 — 목표·진행·결정의 세션 간 연속성
- **3**: P5 + 검사 독립성·충분성 — 계약→누락 표시→검사 약화 방지→실제 환경 실행→버전 결합→아직 모름 유지→잔여 위험 표시. **이 계층 전에 P23 시각 증거를 만들면 안 된다 — 틀린 판정을 더 설득력 있게 보여줄 위험**
- **4**: P15+P14 — 범위·결정 권한의 경계 (성과는 질문 횟수가 아니라 잘못된 권고 거절로 측정)
- **5**: P3/P13+P23 — 이해 가능한 설명·증거 (기계 판정 경계가 선 뒤에)
- **6**: P22+P21 — 복구·외부 노출 안전 (프로덕션·공개·결제·발송·DNS·시크릿 행동보다 반드시 먼저)
- **7**: P6/P7/P8 — 보편 표준이 아니라 공통 최소 바닥 + 유형별 + 위험별 게이트
- **8**: P4/P10 — 전 과정의 성능 제약으로 계측 (C3 검증 전 "절차가 결국 빠르다" 주장 금지)
- **제외/강등**: P9(온디맨드로 축소) · P11(제거) · P19/P20(내부 규율) · G-A(핵심 검증 후)
