# 4잡 vs 1잡 — E-6 실측

> 측정 2026-08-27 · `coolbress/workflows` 의 [`measure-ci-shape.yml`](https://github.com/coolbress/workflows/blob/main/.github/workflows/measure-ci-shape.yml) ·
> 대상 `canary/` · **같은 run 안에서 두 모양을 나란히** · **5회 반복**
>
> [`TEMPLATE-WORKFLOWS-AUDIT`](TEMPLATE-WORKFLOWS-AUDIT.ko.md) **E-6** 을 닫는다.
>
> **왜 재야 했나**: 산출물 바닥의 *"lint·typecheck·test·build 를 각각 별도 required check 로"* 는
> 🔵 **프로젝트 선택**이다 — 코퍼스 처분 `C50-12` 가 ***"4종이 보편"* 을 기각**했다.
> 근거가 없는 자리에서는 **대표 작업으로 재는 것 말고 답이 없다.**

## 측정값 (5회)

| | 벽시계 | 러너 시간(과금 단위) |
|---|---|---|
| **A · 4잡** | **중앙값 11s** (11–12) | **중앙값 36s** (32–39) |
| **B · 1잡 `verify`** | **중앙값 10s** (7–12) | **중앙값 10s** = 벽시계 |
| **차이 (B−A)** | **−1s (사실상 같다)** | **−26s — 1잡이 러너를 28%만 쓴다** |

잡별 중앙값: `a_lint` 10s · `a_test` 10s · `a_typecheck` 8s · `a_build` 8s · `b_verify` 10s.

## 숫자가 아니라 **모양**이 답을 준다

`S` = 준비비용(checkout + setup-uv + `uv sync`), `cᵢ` = 검사 하나의 실제 작업.

| | 벽시계 | 러너 시간 |
|---|---|---|
| **4잡** | `S + max(cᵢ)` | **`4S + Σcᵢ`** |
| **1잡** | `S + Σcᵢ` | `S + Σcᵢ` |

> **4잡이 사는 것**: 벽시계 `Σcᵢ − max(cᵢ)`
> **4잡이 내는 것**: 러너 시간 **`3S` — 작업량과 무관한 고정비**

측정에서 **`S ≈ 8s`** 이고 `Σcᵢ ≈ 2s` 였다. 즉 **1초를 벌려고 24초를 냈다.**
`canary` 는 소스 2개·테스트 1개짜리라 **준비비용이 전부**다.

🔴 **그래서 이 숫자를 큰 프로젝트에 옮기면 안 된다.** `cᵢ` 가 커지면 4잡의 벽시계 이득이 실제로 생긴다 —
검사 하나가 **`S`(≈8s) 수준으로 무거워질 때부터** 4잡이 낸 `3S` 만큼을 벌기 시작한다.

## 판정 — **4잡을 유지한다.** 근거는 속도가 아니었다

측정은 **속도에서 4잡이 유리하다는 통념을 지웠다**(작은 프로젝트에서는 이득이 0이다).
그런데도 유지하는 이유는 셋이고, **그중 어느 것도 속도가 아니다.**

| | 왜 |
|---|---|
| **1. 지금 러너 시간은 공짜다** | 세 저장소 모두 **공개**다(`private=false` 3/3). **3.6배가 $0 × 3.6 = $0** 이다 |
| **2. 실패 진단성** | 4개가 각각 보고하면 lint 가 깨져도 **test 가 통과했는지 보인다.** 1잡은 첫 실패에서 멈춰 나머지 셋의 상태를 **알 수 없다** |
| **3. 바꾸는 비용이 MAJOR 다** | 검사 이름이 `ci / lint` → `ci / verify` 로 바뀐다. **룰셋의 required context 4개**와 **모든 소비자**가 같이 움직여야 하고, 어긋나면 저장소가 **조용히 머지 불가로 잠긴다** |

> **⚠️ 이것은 *"4종이 보편"* 의 부활이 아니다.** `C50-12` 의 기각은 그대로다.
> 여기서 선 것은 ***"우리 상황(공개 저장소 · 작은 프로젝트 · 솔로)에서는 4잡이 낫다"*** 까지다.
> 🔵 **판단**이 🟡 **측정된 판단**이 됐을 뿐 🟢 이 된 것이 아니다.

## 다시 열 조건 — **미리 박는다**

1. **프로젝트가 비공개가 되고** CI 가 자주 돌 때 — 그때 **3.6배가 실제 분(minute)이 된다**
2. **준비비용 `S` 가 커질 때**(무거운 의존성) — `4S` 가 전체를 지배한다
3. 반대로 **검사 하나가 무거워질 때**는 4잡이 **더** 유리해진다 — 그때는 다시 안 열어도 된다

**재는 법은 남겨 뒀다**: `gh workflow run measure-ci-shape.yml -f round=N` 을 몇 번 돌리고
잡별 `started_at`/`completed_at` 을 읽는다. **두 모양이 같은 run 안에 있어야** 비교가 성립한다 —
다른 날 따로 돌린 값은 측정이 아니라 일화다.
