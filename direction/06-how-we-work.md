## 사용자는 스킬 이름과 순서를 외우지 않는다

**흐름 지도는 새로 만들지 않는다.** [`ask-matt`](https://github.com/mattpocock/skills/blob/main/skills/engineering/ask-matt/SKILL.md)
이 이미 아이디어→출시의 큰 흐름과 온램프와 분기 조건을 갖고 있다. **프로그램이 아니라 Markdown 지도 한 장**이고,
모델이 읽고 판단한다. 라우팅의 상당 부분은 **Claude Code 기본 기능**도 담당한다 — model-invoked 스킬은
`description` 의 조건을 보고 모델이 고른다.

> 우리에게 새로 필요한 것은 큰 Router 가 아니다.
> **`ask-matt` 이 모르는 *"이 프로젝트가 지금 어디까지 왔는가"* 를 읽는 작은 조각뿐이다.**

### 진입로는 둘이다

| 사용자가 한 말 | 시작되는 것 |
|---|---|
| `/ask-matt` | 기존 Markdown 흐름 지도가 알맞은 flow·skill 을 안내 |
| *"이 프로젝트 시작하자 · 계속 진행해줘"* | **읽기 전용 상태 probe** 가 정본을 읽어 현재 단계를 판별 |

자연어 진입로가 `ask-matt` 을 몰래 실행하는 것은 아니다. probe 가 단계를 찾고, 모델은 skill description 으로
다음 능력을 고른다. **다음이 user-invoked 스킬이면 실행한 척하지 않고 사용자가 누를 명령을 알려준다.**

### 🔴 Router 가 절대 가지면 안 되는 것

probe 는 **읽기 전용**이다. `.router-state.json` 같은 전용 상태 파일 금지 · Issue·PR·CI 와 **경쟁하는 두 번째 진실** 금지 ·
매 턴 도는 별도 제어 루프 금지 · 자체 DB·queue·retry engine·결과 취합 runtime 금지.

> **Router 는 상태를 소유하지 않는다. 이미 존재하는 진실을 읽고 다음 능력으로 연결할 뿐이다.**
> **전용 상태나 독립 제어 루프가 생기면 일곱 번째 하네스가 시작된 것이므로 제거한다.**

🟢 **이 기준이 줄 수보다 낫다** — [`02`](02-why-past-attempts-failed.md) 의 판별식(*"런타임에 도는가"*)을
**방향으로** 바꾼 것이다. `ask-matt` 형태의 문서는 안 돈다.

> 🔴 **경계를 정확히 긋는다 — 쓰기 자체가 하네스인 것이 아니다.**
> **Router 가 *자기* 상태를 소유하거나 독립 제어 루프를 가지면 하네스다.**
> **호출된 능력이 *이미 있는* 정본(Issue·PR·handoff)을 갱신하는 것은 정상 작업이다.**
>
> 이 구별이 없으면 아래 §자동/사람 표(호출된 스킬의 정본 갱신 = 자동 허용)와 정면으로 충돌한다.
> **handoff 도 Router 상태가 아니다** — 정본이 **어디에 있는지**를 가리키는 작은 바통이지,
> 정본과 경쟁하는 두 번째 진실이 아니다.

### 상태를 보면 다음 일이 보인다

| 지금 모습 | 다음 행동 |
|---|---|
| 새 프로젝트인데 목적이 흐림 | **기존 해결책 조사** → 인터뷰 → Brief·AC |
| 목적은 있지만 할 일이 안 나뉨 | 작은 티켓으로 나누기 |
| 티켓과 완료 조건이 준비됨 | 구현·TDD 스킬로 만들고 검사 |
| 화면 작업 | 프론트엔드 스킬 **하나** + 브라우저 검사 |
| 구현은 끝났는데 검토가 없음 | 독립 리뷰 → PR → CI |
| 이전 세션에서 멈춤 | 정본을 읽고 그 자리부터 |
| 아주 작은 수정 | **인터뷰와 조사를 건너뛴다** |

### 자동으로 해도 되는 일 vs 사람이 정해야 하는 일

| 에이전트 자동 | 사람이 결정 |
|---|---|
| 저장소·문서 읽기 · 실패한 테스트 찾기 · 기존 해결책 조사 | **누구의 어떤 문제인지** · 범위와 비범위 |
| 필요한 스킬 호출 · 테스트·타입·린트·빌드 실행 | 큰 구조와 비용 · **개인정보·보안 위험 수용** |
| 호출된 스킬이 Issue·PR·handoff 같은 **정본** 갱신 | **공개·배포·머지** · 관리자·프로덕션 권한 사용 |

## 프로젝트는 이 순서로 간다

모든 프로젝트가 똑같이 무겁게 움직이지 않는다. 하지만 큰 길은 같다.

| 단계 | 무엇을 | 근거 |
|---|---|---|
| **1. 이미 있는지 찾는다** | 같은 문제를 푸는 제품·도구가 있나 · 프로젝트 안에 이미 있나 · **직접 만든다면 왜 기존이 부족한지 적는다** | 대전제 1 · [`SKILL-OVERLAP`](../audit/SKILL-OVERLAP.ko.md) 실측 |
| **2. 무엇을 만들지 분명히** | 누구의 어떤 문제 · 왜 지금 · 성공하면 뭐가 달라지나 · **안 만들 것** · 완료를 무엇으로 확인 · 위험과 가정 | 🟢 `ELI-001` — **실수 목록을 쥐여주면 LLM 후속질문이 사람을 이긴다**(통제실험 2개) |
| **3. 작은 일로 나눈다** | 짧은 스펙 · **하지 않을 일** · 완료 조건↔검사 연결 · 중요한 선택만 ADR · **첫 조각은 end-to-end 한 줄기** | 🟡 walking skeleton([`05`](05-the-output-floor.md) 테스트 묶음) |
| **4. 프로젝트를 준비한다** | 새 Python 이면 template + bootstrap · **기존 프로젝트면 덮어쓰지 않는다** — 먼저 어떻게 돌고 테스트되는지 본다 | [`05`](05-the-output-floor.md) |
| **5. 작게 만들고 바로 검사** | 가능하면 실패하는 테스트부터 · 가장 작은 변경 · 관계없는 정리를 섞지 않는다 · **경고를 숨기지 않는다** | 🟡 `TDD-001·002` — **순서는 권고, 동반은 강제.** 문서·설정 변경까지 RED→GREEN 을 강제하지 않는다 |
| **6. 다른 눈 + GitHub 검사** | 작성자와 **다른 관점**으로 diff · PR 에 무엇을 왜·어떻게 확인했는지 · **CI 빨간불이면 머지 안 한다** | 🟢 `IPW-006`(컨텍스트 분리가 원인) · 🟡 `IPW-007`(**오류 71% 를 놓친다 — 안전망이 아니다**) · 🟢 `AGP-001`(에이전트 PR 33k — **CI 가 머지를 가른다**) |
| **7. 필요한 프로젝트만 배포 확인** | 로컬 도구에 배포 과정을 억지로 붙이지 않는다. 실제 서비스면 배포 자동화·health·롤백·개인정보·비용 | [`05`](05-the-output-floor.md) 아키타입 층 |
| **8. 다음 세션에 바통** | **이전 채팅을 기억한다고 믿지 않는다.** Issue·PR·스펙·ADR·CI·handoff 를 읽으면 이어서 일할 수 있어야 한다 | 요구 ④ |

### 상태는 채팅 밖에 남긴다

에이전트의 기억만 믿으면 세션이 바뀔 때 길을 잃는다.

| 기억할 것 | 남길 곳 |
|---|---|
| 목적과 안 할 일 | Project Brief · 스펙 |
| 지금 하는 일 | **GitHub Issue** |
| 완료 조건 | AC ↔ 검사 연결표 |
| 큰 선택의 이유 | ADR |
| 코드 상태 | Branch · PR |
| **실제 판정** | **CI** |
| 다음 세션 안내 | handoff 파일 하나 |

🔴 **파일이 있기만 해서는 부족하다.** `presence ≠ adequacy` — 야생 실측으로 **CONTRIBUTING 이 있는 것 중 1/3 이 스텁**이다([`05`](05-the-output-floor.md) §근거).

## 모델과 여러 에이전트는 작업 성질로 고른다

**예산이 둘이고 서로 반대로 움직인다.**

| 예산 | 뜻 |
|---|---|
| **총 토큰** | 모든 모델이 합쳐 쓴 비용 |
| **브레인 컨텍스트** | 목적과 결정을 기억하는 메인 창의 남은 공간 |

에이전트 하나가 다 읽으면 총 토큰은 적지만 **긴 자료가 브레인 창에 쌓인다.** subagent 가 자기 창에서 조사하고
짧은 결과만 돌려주면 **총 토큰은 늘고 브레인 창은 오래 쓴다.**

🟡 **수치**(`MAO-002`): chat 대비 단일 agent **약 4배** · multi-agent **약 15배**. 그리고 **BrowseComp** 평가에서
세 요인이 성능 분산의 95%를 설명하고 **토큰 사용량만으로 80%**를 설명했다. ⚠️ **90.2%(내부 research eval)와는 다른 평가다.**

🟡 **그리고 이 숫자는 코딩의 법칙이 아니다** — 넓은 웹 조사용 시스템의 값이고, 원문 자신이 **코딩은 병렬 가능한
하위작업이 적다**고 비교문으로 말한다(`MAO-005`).

> **그래서 기본은 에이전트 한 명이다.**
>
> ⚠️ **이것은 처음 의도와 반대다.** 소유자의 처음 진술은 *"멀티 에이전트를 **적극 활용**"* 이었고,
> 근거를 확인한 뒤 *"기본은 한 명, 조건이 맞을 때만 여럿"* 으로 뒤집혔다.
> **버린 것이 아니라 조건을 붙인 것이다** — 그 진술이 원한 것(토큰 효율 · 관점의 변증법)은
> 아래 네 질문과 담당표에 그대로 살아 있고, [`01`](01-what-i-want.md) **요구 5(오케스트레이션)** 가 그것을 받는다.
> 다시 뒤집을 조건: **대표 작업으로 잰 결과가 여럿 쪽이 낫다고 나오면 바꾼다.**

### subagent 를 쓰는 네 질문 — 모두 "예" 일 때만

1. 다른 일과 **독립적으로** 진행할 수 있는가?
2. 긴 결과를 **짧게 압축**해 돌려줄 수 있는가?
3. 테스트·출처·로그로 **따로 검증**할 수 있는가?
4. 다시 합치는 비용보다 **브레인 컨텍스트를 아끼는 이득**이 큰가?

하나라도 "아니오"면 브레인이 직접 하거나 일을 더 작게 나눈다.

### 병렬이 아닌 것을 병렬이라 부르지 않는다

- **다른 subagent 의 아직 안 끝난 결과를 기다려야 한다면 그건 병렬이 아니다.** 순서가 있는 일을 나눠 띄운 것뿐이고,
  브레인 창에 대기 비용만 더한다.
- **같은 파일·같은 상태에는 작성자를 한 명만 둔다** (원칙 04 의 단일 작성자 · `MAO-004`).
- **단순한 작은 일은 위임하지 않는다.** 되돌려 읽는 비용이 직접 하는 비용보다 크다.
- 🔴 **비용이 큰 Agent Team 은 일반 subagent 와 다르다** — **에이전트끼리 직접 협의해야 할 때만** 쓴다.
  브레인이 결과를 받아 합치면 되는 일이면 그건 subagent 로 충분하다.

### 무엇을 누가 맡나

| 작업 | 기본 담당 |
|---|---|
| 짧은 파일 하나 확인 · 여러 모듈을 함께 바꾸는 구현 · 결과 취합과 충돌 해결 | **브레인** |
| 여러 공식 자료 조사 · 겹치지 않는 코드 영역 조사 · 버그 재현과 원인 후보 | **subagent** |
| 독립적인 공격 리뷰 | **reviewer subagent** (🟢 `IPW-006`) |
| 경계가 분명한 독립 모듈 구현 | subagent 가능 |
| 여러 해결 방법 비교 | subagent 제안 → **브레인 결정** |
| 핵심 아키텍처 결정 | **브레인 + 사람** |
| **성공 여부 판정** | **테스트·CI** — 모델의 자신감이 아니다 |

***"읽기는 subagent, 쓰기는 브레인"* 은 좋은 시작 규칙이지 절대 규칙이 아니다.** 쓰기도 AC 가 분명하고 ·
파일 경계가 분리돼 있고 · 쓰기 영역이 안 겹치고 · 테스트로 독립 검증되고 · 브레인이 통합할 수 있으면 맡길 수 있다.

🟡 **한 작업 공간에는 작성자 한 명**(`MAO-004` — 인용은 정확하나 근거는 **자사 운영 경험**이다).

### subagent 가 돌려줄 작은 꾸러미

**긴 작업 기록을 브레인에 그대로 넣지 않는다.** ① 결론 ② 근거와 출처 ③ 바꾼 파일·확인한 범위
④ 실행한 테스트와 결과 ⑤ 남은 불확실성과 위험. 원문이 중요한 결과는 **파일·PR 에 남기고 경로만** 돌려준다.

### 브레인 창이 부족할 때

**컨텍스트가 부족하다는 이유만으로 얽힌 구현을 억지로 나누지 않는다** — 전달에서 맥락이 사라지고 충돌이 는다.
대신 ① 정본에 사실을 남기고 ② handoff 에 **위치와 바로 다음 일만** 적고 ③ 새 세션이 정본을 읽고 잇는다.

> **subagent 는 컨텍스트 압축을 피하는 유일한 도구가 아니다.**

### 모델 강점표는 임시 가설이다

*"Fable 은 계획, GPT 는 구현"* 처럼 **모델 이름으로 역할을 영구 고정하지 않는다.** 대표 작업 5~10개로 시험하고 ·
성공률·수정 횟수·시간·토큰·비용을 적고 · **모델뿐 아니라 하네스와 도구 버전도** 적고 · 새 모델이 나오면 다시 시험한다.

**Herdr 는 두뇌도 라우터도 아니다** — multi-agent 가 선택된 실행에서 **사용자가 각 pane 을 직접 보는 관찰 창**이다.

## 결정을 언제 회부하고 언제 안 하나 (2026-08-29 신설)

**회부는 `decision` 라벨 이슈로 한다** — 대화는 요약이고 **정본은 이슈**다. 근거와 계기는
[`direction/04` §판정 기준](04-the-plan.md)에, 세는 도구는 `tools/check_decision_referrals.py` 에 있다.

### 종류가 셋이다 — 트리거도 대기 방식도 다르다

HITL 분류(12-Factor Agents Factor 7 계열)를 그대로 쓴다. 한 통에 담으면 **긴급도가 안 보인다.**

| 라벨 | 무엇 | 트리거 |
|---|---|---|
| `decision:approval` | 되돌리기 어려운 행동의 가부 | 비가역 · 외부 통신 · 권한 변경 · 벽 변경 |
| `decision:input` | 에이전트에게 없는 **정보·취향** | 두 길이 다 정당하고 소유자 선호가 갈린다 |
| `decision:escalation` | **막혔다** | 권한 없음 · 반복 실패 · 예상 못 한 상태 |

### 🔴 묻지 말아야 할 것 — **과다 회부가 실패 모드다**

원문이 코드로 나쁜 예를 든다 — 항목마다 승인을 요청하면 *"approval fatigue leads to
**rubber-stamping**"*. 그러면 **계기는 초록인데 감독은 없다.** 처방은
*"batch into single meaningful approval"* 이고, 아래는 **아예 묻지 않는다**:

- **읽기 전용** · 조사 · 측정
- **되돌리기 쉬운 저위험** 변경
- **이미 정착된 패턴 안의 행동** — 오늘 이 저장소에서 한 대부분이 여기다
  (검사 하나 더 달기 · 격차 하나 닫기 · 브랜치→PR→CI→머지)
- 진행 확인(*"이 순서로 갈까요"*) — 그건 회부가 아니라 **보고**다

**묻는 것은 셋뿐이다** — 되돌리기 어렵거나 · 소유자 취향이 갈리거나 · **내가 권한이 없거나.**

### 답이 오면 — **채널을 적는다**

원문: *"Log everything — who approved what, when, **via which channel**."*
🔴 **대화로 온 답을 내가 옮겨 적으면, 내가 정확히 옮겼는지를 아무도 검증할 수 없다.**
그래서 답 코멘트에 **`채널:` 한 줄**을 같이 남긴다.

### 그리고 **결정은 커밋된다**

RFC(제안·검토 중)는 이슈에 살아도 된다 — 코퍼스가 *"RFC 는 general documentation, ADR 은 저장소 가까이"*
로 가른다. 🔴 **다만 결정이 서면 `direction/` 이나 `audit/` 에 들어가야 한다.** 이슈는 저장소 밖이라
diff 도 PR 리뷰도 없고, 그게 코퍼스가 위키를 물리치며 든 이유다.
검사가 *"닫힌 회부의 번호가 커밋된 기록에 있나"* 를 본다 — **그 다리가 없으면 *왜* 가 저장소 밖에만 남는다.**

## 로컬은 초록인데 CI 만 빨간 것 — **재현하는 법** (2026-08-29 신설)

하루에 **세 번** 겪었다. 전부 *환경이 시험의 일부*라는 같은 이야기이고,
**세 번 다 CI 가 먼저 잡았다.** 🔵 **그게 CI 의 일이므로 여기에 또 하나의 검사를 만들지 않는다** —
대신 **의심될 때 로컬에서 재현하는 방법**을 적는다. 아래 셋은 실제로 그날 써서 통한 것이다.

| 무엇이 달랐나 | 어떻게 재현하나 | 그날의 사건 |
|---|---|---|
| **체크아웃 깊이** — `actions/checkout` 은 기본이 `fetch-depth: 1` | `git clone --depth 1 "file://$PWD" /tmp/x && cd /tmp/x && uv run pytest` | copier 가 `ShallowCloneWarning` 을 냈고 `filterwarnings=["error"]` 가 그걸 에러로 올렸다 |
| **GNU vs BSD 도구** — CI 는 ubuntu, 로컬은 macOS | `brew install coreutils` 후 `gtr`·`gsed` 로 같은 줄을 돌려본다 | `tr '.- '` 를 BSD 는 받고 **GNU 는 범위로 읽어 거부**했다 |
| **네트워크·자격증명 없음** | 단위 시험은 **네트워크를 타면 안 된다.** 서버 사실은 `tools/repo_audit.py` 가 본다 | 라벨 설치 확인 시험이 `gh` 를 탔다 |

⚠️ **그리고 이건 환경 문제가 아니었지만 같은 날 같은 뿌리에서 나왔다** — 어떤 계산이
**빈 입력에서만 통과**하고 있었다(`(comments or 0) > 0` 이 빈 리스트에선 `0 > 0`, 값이 들어오자 `TypeError`).
🔴 ***실행되지 않은 경로의 초록은 증거가 아니다*** — 코퍼스의 `green≠증거` 그대로다.
**빈 경우와 값이 있는 경우를 둘 다 돌린다.**

## 조사 방법은 여기 없다

*"어떻게 조사하고 무엇을 믿는가"* 는 이 문서가 규정하지 않는다.
[`corpus/methods/reverification-protocol.md`](../corpus/methods/reverification-protocol.md) 가 정본이다 —
인용 사슬 펴기 → 주장 종류 분류 → **1차 출처 직접 읽기** → 독립 검증자 → 갈리면 충돌 등재 → 전파된 곳까지 수정 → 기록.

⚠️ **인기는 힌트지 진실 판정이 아니다.** `last30days` 같은 도구는 **후보와 검색어를 찾는 데** 쓰고,
판정은 공식 문서·1차 출처·로컬 실험으로 한다. 보안·법·규정에서는 **공식 자료가 중심**이다.
