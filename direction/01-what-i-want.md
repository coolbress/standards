## 가장 중요한 네 가지 규칙

### 규칙 1. 만들기 전에 먼저 찾는다

> Claude Code 기본 기능 → 현재 프로젝트 → GitHub·언어의 표준 기능 → 기존 스킬·플러그인 → 작은 연결부 → **그래도 없을 때만** 직접 개발

### 규칙 2. 작고 가볍게 만든다

새 도구는 이 여섯을 만족해야 한다 — **필요할 때만 켠다 · 평소에 긴 내용을 계속 읽히지 않는다 ·
빼도 프로젝트가 안 망가진다 · 버전이나 커밋을 기록한다 · 실제 작업으로 효과를 확인한다 ·
더 좋은 기본 기능이 생기면 없앤다.**

### 규칙 3. 도움과 강제를 구분한다

> **스킬은 선생님이고, CI 와 Ruleset 은 통과문이다.**

| | 하는 일 | 성격 |
|---|---|---|
| 스킬 | 잘하는 방법을 알려준다 | 🤝 도움 |
| Hook | 실수를 빨리 알려준다 | 🤝 도움 |
| Template | 좋은 시작 파일을 준다 | 📋 1회 |
| CI · Ruleset | **틀린 결과가 머지되지 못하게 막는다** | 🔒 강제 |
| 권한 분리 | **에이전트가 그 문을 몰래 열지 못하게 한다** | 🔒 강제 |

🟢 **로컬 훅은 강제가 될 수 없다** — git 자체 문서: `--no-verify` 는 *"bypasses the pre-commit and commit-msg hooks"* (`IPW-005`).
그래서 **중요한 규칙은 GitHub 서버에서 막는다.** 이 저장소에서 **벽 4/4 실물 확증**(직접 푸시·빨간불·소유자 `--admin` 전부 거부)이 그 증거다.

🔴 **이 구분이 도구 선택을 가른다.** 스킬 카탈로그 대조에서 **🔒 층은 0% 겹쳤고 🤝 층은 100% 겹쳤다** —
**안내는 이미 있는 것을 쓰고, 벽은 아무도 대신 만들어 주지 않는다.**

### 규칙 4. 사람은 방향을 정하고 에이전트는 노동한다

에이전트가 **목적을 대신 정하면 안 된다.** 에이전트는 내가 정한 목적을 작은 일로 바꾸고, 실행하고, 검증하는 조력자다.
🟡 판단을 위임하지 않는 근거는 [`04`](04-the-plan.md) 원칙 04 에 있다(`MAO-004` — 인용은 정확하나 **자사 운영 경험**이다).

## 도구 창고와 오늘의 도구 가방

**Arsenal 은 큰 도구 창고다** — 현재 쓰는 것만이 아니라 **발견한 것 · 시험 중인 것 · 보류한 것 · 버린 것**도 기록한다.
현재 실물은 [`SKILL-OVERLAP`](../audit/SKILL-OVERLAP.ko.md)이다.

**Loadout 은 오늘 필요한 도구만 담은 가방이다.** 모든 도구를 항상 켜지 않는다 — 그것이 대전제 2를 실행 가능하게 만드는 장치다.

| 오늘 하는 일 | 가방 |
|---|---|
| 짧은 문서 수정 | 에이전트와 주 모델 |
| Python 기능 구현 | 주 모델 + 구현·TDD 스킬 + CI |
| 랜딩 페이지 | 위 + **프론트엔드 스킬 하나** + 브라우저 검사 |

| 작은 버그 수정 | 한 에이전트 + 재현 테스트 |
| 여러 갈래의 넓은 조사 | 브레인 + 갈래별 subagent |
| 독립 코드 리뷰 | 구현 에이전트 + **별도 reviewer subagent** |

**같은 일을 하는 후보는 하나만 켠다** — Taste·Impeccable·frontend-design 을 동시에 켜지 않는다.
반대로 **Fable 과 Ponytail 은 경쟁 후보가 아니다**(하나는 모델, 하나는 작업 설명서).

### 요구 1이 뜻하지 **않는** 것 — 두 경계

요구 1(*팀처럼 만든다*)은 커버 범위가 가장 넓고(층1 문제 16개), 그만큼 **잘못 읽히기 쉽다.**
두 가지는 뜻하지 않는다.

**① 절차를 흉내내는 것이 아니다.**

- 🟢 **하중을 받는 것은 *"브랜치 수명 단축 + 매일 통합"* 이라는 행동**이지 모델의 이름이 아니다 —
  DORA 의 **≤3 활성 브랜치 · 하루 1회 이상 병합**이 받친다. 🟡 단 **설문 분석의 상관**이지 저장소 계측이 아니다 (`GHW-009·010`).
- 🔵 *"브랜치 다이어그램을 정교하게 그리는 것 자체는 ceremony다"* — **판단이다.** 그 행위를 측정한 연구를 찾지 못했다.
- 🟡 **무거운 리뷰는 trunk 기반 개발의 장애물이다** — DORA 가 *"An overly heavy code-review process …
  **requires multiple approvals**"* 를 *Common pitfalls* 로 든다. **단 범위가 좁다**: *코드리뷰 일반의 안티패턴*이 아니라
  *TBD 채택의 장애물*이고, **체크리스트는 그 페이지에 없다** (`GHW-011`).

→ 그래서 [`04`](04-the-plan.md)는 절차 이름이 아니라 **수치**를 박는다: diff 200줄 목표·400줄 상한 ·
CI 10분(🟡 XP 가이드라인이지 측정된 임계가 아니다 · `CIB-001`) · 이슈는 크기 조건부.
상세는 [`03`](03-what-research-says.md).

**② 사람 동료 리뷰를 시뮬레이션하는 것이 아니다.**
이 프로젝트는 **1인**이다. 코퍼스가 그 한계를 직접 규정한다:

> *"1인 프로젝트에서 독립적인 사람 승인은 불가능할 수 있다. **그 한계는 시뮬레이션하지 말고 명시해야 한다.**
> 자동 검사·보호된 머지·독립 모델 리뷰가 위험을 줄일 수는 있으나 **책임 있는 동료 리뷰와 동등하지 않다.**"*
> — [`corpus/aspects/05-scm-workflow/github-workflow-current.md`](../corpus/aspects/05-scm-workflow/github-workflow-current.md)

→ 그래서 룰셋은 `required_approving_review_count: **0**`이다. 솔로는 자기 PR을 승인할 수 없으므로
**승인 도장을 흉내내는 대신 CI를 진짜 게이트로** 쓴다. `@claude` 리뷰는 *다른 컨텍스트의 제3자*이지
*사람 동료가 아니다* — 이 구분을 지우지 않는다.

**이 두 경계를 지우면 goppi의 실패가 재발한다.** goppi G4의 승인 산물은 *"사람이 창을 눌렀다"* 를
증명하지 못했는데 증명하는 것처럼 취급됐다 — 시뮬레이션된 승인이 실제 승인 자리에 앉은 것이다
([`legacy/LINEAGE.md`](../legacy/LINEAGE.md) §5).

### 요구 3이 왜 하나인가

*판독*과 *결정*은 갈라놓을 수 없다 — **읽지 못하면 결정할 수 없기 때문이다.**
문제 지도가 이 둘을 나란히 놓는다: P28(*이해 못 한 채 결정할 위험*)이 P13(*쉬운 설명이 기본값이 아니다*)의
결과이고, P44(*결정 화면이 편향을 유도*)는 P14(*선택지·근거·위험이 안 드러남*)와 시험을 공유한다.
그리고 P40의 주석이 이 요구의 지위를 정한다 — *"§1 **'정말 필요한 판단만'** 의 근거"*.

### ⭐ 승격 기록 — 요구 5 (오케스트레이션)

문제 지도는 **P11을 층2("있으면 좋은 것")** 로 배정했다. 그 판정은 **2026-08-13 goppi 맥락**의 것이다 —
당시엔 하네스가 알아서 배치해주면 좋은 부가 기능이었다.

**2026-08-24, 소유자가 이를 요구로 재확인했다.** 상위 모델이 브레인으로 앉아 하위·외부 모델에
작업을 배분하는 것은 부가가 아니라 **하려는 일 자체**다.

- **문제 지도는 고치지 않는다** — append-only이고 `[1차]`는 소유자만 수정한다. 층2 배정은 그대로 둔다.
- **`direction/`이 현행이다.** 이 승격은 **소유자 결정(2026-08-24)** 이며 근거는 소유자 진술이다 —
  *"프로젝트 판단"* 으로 명시한다(근거를 가장하지 않는다).
- 다만 **순서상 마지막**인 것은 유지한다. 방향과 안전망이 선다.

## 왜 문제 지도는 `direction/`이 아니라 `corpus/`에 있나

**증거와 결론을 섞지 않기 위해서다.** 문제 지도는 *"이런 문제가 실재한다"* 는 수집된 증거이고
(출처×검증 2축 등급 · `[1차]`는 소유자만 수정 · append-only),
이 문서는 *"그래서 이렇게 한다"* 는 결론이다 — rev를 올려가며 고친다.

역사가 이 분리를 요구한다: 원래 문제 지도는 Codex 적대 검수에서
*"문제·증거·원인 가설·설계 제약·해결책·내부 개발 규율이 한 번호 체계에 섞여 있다"* 는 이유로
**반려당했고**, 5층 재구성이 그 처방이었다
([`review--codex-rejection-1-2026-08-12.md`](../corpus/census-data/owner-problem-map/review--codex-rejection-1-2026-08-12.md)).
