## 📦 상자는 **생태계마다 하나** — 한 템플릿에 다 담지 않는다 (2026-08-30 결정)

`project-template` 은 **파이썬 패키지 생성기**다(`pyproject.toml` · `hatchling` · `uv.lock` ·
`python-ci.yml`). 그런데 아키타입 선택지에 **웹 프론트엔드**와 **모바일**이 있었고,
고르면 나오는 건 **그냥 파이썬 패키지**였다 — **질문이 기계가 지킬 수 없는 답을 제시하고 있었다**
(`GAPS` R5-41 · 실물 증거: `mobile` 이 바닥의 어느 조건부 항목에도 안 걸렸다).

### 왜 조건부로 안 넣나 — **바뀌는 게 파일이 아니라 층 넷이다**

| | `backend` 에 `Dockerfile` | `web` 프론트엔드 |
|---|---|---|
| 뼈대 | `pyproject.toml` 그대로 | 🔴 `package.json` · `tsconfig` · 번들러 |
| 락파일 | `uv.lock` 그대로 | 🔴 `pnpm-lock.yaml` |
| CI | `python-ci.yml` 그대로 | 🔴 **`node-ci.yml` 을 새로 써야 한다** |
| 벽 | 검사 이름 그대로 | 🔴 **룰셋의 요구 검사 이름이 통째로 달라진다** |
| 시험 | 그대로 | 🔴 `test_*.py` 전부 무의미 |

`Dockerfile` 은 **파일 하나 더**라 `_exclude` 한 줄이면 된다. 생태계는 다르다 —
한 템플릿에 둘을 담으면 `_exclude` 가 **대부분의 파일에 걸리고** 유지가 안 된다.

### 그래서 이렇게 간다

```
🔒 벽 · 🤝 안내        ← 언어 무관. **그대로 재사용된다**
   ├ 📦 project-template        (파이썬: cli · library · backend · data-ml)
   ├ 📦 project-template-node   (아직 없다 — 프론트엔드를 실제로 시작할 때)
   └ 📦 …                        생태계마다 하나
```

🔴 **고르는 것은 에이전트다.** `/kickoff` 이 프로젝트의 종류를 이미 끌어내므로,
그 답에 맞는 **상자를 골라 `/new-project` 에 넘긴다.** 사용자가 생성기 이름을 알 필요가 없다.
⚠️ **없는 생태계는 없다고 말한다** — `--private` 를 받는 척하지 않고 거부하는 것과 같은 규율이다.
받는 척하는 것이 이 프로젝트가 죽는 방식이다.

🔵 **지금 좁힌 것은 기능을 뺀 게 아니라 거짓말을 없앤 것이다.** 고를 수 있는데 안 나오는 상태보다
안 된다고 말하는 쪽이 낫다. 두 번째 상자는 **실제로 그 프로젝트를 시작할 때** 만든다 —
지금 만들면 검증할 인스턴스가 없어 스텁이 된다.

## ⑩ 재판정 (2026-08-29) — **새 잡을 짓는 대신 있는 둘에 붙였다**

착수 첫 일로 *"이미 덮인 게 뭔가"* 를 셌다(대전제 1 — 있는 걸 다시 만들지 않는다). **실측:**

| ⑩ 이 보겠다던 것 | 이미 덮였나 | 무엇이 |
|---|---|---|
| 락파일 커밋 | ✅ **네 번** | `uv sync --locked` 가 `lint`·`typecheck`·`test`·`build` **전부**에 — *"락파일이 없거나 `pyproject` 와 어긋나면 실패한다"* |
| Actions SHA 핀 | ✅ **더 강하게** | **서버**가 강제하고(`sha_pinning_required`) `repo_audit` 이 감사한다. CI 잡보다 세다 — **에이전트가 못 끈다** |
| `.env.example` | ✅ **내용까지** | 템플릿의 `tests/test_env_example.py` 가 *코드가 읽는 변수를 전부 문서화했나* 를 본다 |
| `.env` 가 실제로 추적되나 | 🔴 **구멍** | `.gitignore` 는 **예방이지 보증이 아니다** — `git add -f` 가 넘고, 규칙보다 먼저 커밋된 파일은 남는다 |
| 조건부(`migrations/`·`openapi.*`) | — | **해당 아키타입의 프로젝트가 아직 없다** |

**그래서 처분은 둘로 갈렸다** — 새 CI 잡을 지으면 원칙 2(*무겁게 만들지 않는다*)와 대전제 1에 함께 걸린다:

- **ⓐ 인스턴스 안** → 템플릿 시험 `tests/test_tree_hygiene.py`(`.env` 추적 · 바이너리 산출물).
  **CONTRIBUTING 과 같은 처분**이고, 인스턴스가 지우면 `check_template_drift` 의 `missing_files` 가 잡는다
- **ⓑ 저장소 밖** → `check_template_drift` 가 **잉여 파일**도 본다. 예전엔 *템플릿에서 인스턴스를 뺀 것*

**소유자의 유일한 실제 웹 프로젝트에서 통과할 수 없고**, 그 저장소는 첫 PR 부터 영구 차단된다 —
**`uv sync --locked` 로 이미 겪은 것과 같은 형태**다(만들 것 3 이 *"도는 프로젝트"* 여야 했던 이유).

**그리고 순서가 맞지 않는다.** 완주를 한 번도 못 한 상태에서 스택을 늘리는 것은
이 문서의 *"벽보다 도구를 먼저 늘리기 ✕"* 에 정면으로 걸린다. 웹 프로젝트는 **아직 GitHub 에 있지도 않다** —
없는 저장소를 위해 워크플로를 먼저 만드는 셈이다.

**다시 여는 조건**: `divtadel`(또는 다른 웹 프로젝트)이 **실제로 원격에 올라갈 때.**
그때 열어야 할 질문은 *"web-ci.yml 을 만들까"* 가 아니라 순서대로 이 둘이다 —
① **그 프로젝트에 lint·test 를 먼저 넣는다**(없으면 4검사가 성립하지 않는다)
② 브라운필드 도입 경로를 쓴다([`brownfield-adoption-floor`](../corpus/aspects/04-build-ci-engineering/brownfield-adoption-floor.md) *(review-needed)* — **절차 포인터이지 근거 인용이 아니다**) —
`new-project.sh` 는 템플릿에서 **새로** 뜨는 도구라 기존 프로젝트에 쓸 수 없다.

> **루프 1회 통과 (2026-08-24)**: `new-project.sh` → 이슈(AC) → 브랜치 → PR → CI 4/4 → 머지 → 이슈 종료.
> 새 저장소에서 **벽 4/4 재확증**(직접 푸시·빨간불·소유자 `--admin` 전부 거부).
> ⚠️ **완료의 정의는 아직 미충족** — 시험 저장소가 임시 프로브였고 `/kickoff`(④)를 태우지 않았다.
> **기계 구간만 검증됐고 *아이디어 → 과제 번역* 구간은 미시험이다.**

> **②에서 나온 실측 하나가 ③·⑤를 구속한다**: 재사용 워크플로의 검사 이름은
> `{호출잡}/{피호출잡}` 이다([`cross-project-reuse--facts-2026-08`](../corpus/aspects/04-build-ci-engineering/cross-project-reuse--facts-2026-08.md) *(draft)* `CPR-007`·`CPR-008`).
> 호출잡 이름이 required context 의 일부이므로 **템플릿과 룰셋이 그 이름으로 묶인다.**

## 판정 기준 — 사전 등록 (2026-08-24)

> 확증시험이 했던 것과 같은 수준으로 **미리** 박는다. **결과를 보고 기준을 옮기지 않는다.**
> 첫 판은 요구 4 하나만, 그것도 자기보고로 다뤘다 — `03`이 인용하는 원칙
> (*"검증은 객관 신호로 — 자기평가는 신뢰할 수 없다"*)과 정면 충돌이었다.

> 🎯 **선행 조건 — 완료의 정의**: 만들 것 ②③⑤가 끝나면 **새 프로젝트 하나를 end-to-end로 돌린다.**
> `new-project.sh` → `/kickoff` → 이슈 → PR → CI → 머지가 **한 번 통과할 때까지 ①~⑤는 미완**이다.
> `coolbress/standards` 안에서의 검증은 **합성 시험**이다 — 이 저장소는 문서 저장소라
> 락파일·테스트 스위트가 없어 바닥 검사 대부분이 적용되지 않는다.
> **goppi가 합성 공격 0/4를 막고 실사용 11건에 침묵한 것과 같은 형태를 피하기 위해서다.**

**관찰 기간**: 실사용 2주 (위 end-to-end 통과 **이후**부터 센다).

**기록 수단** — 지표마다 다르다. *"이미 남는 것만 쓴다"* 는 ①②⑤에만 참이다(2차 검수 지적):

| 지표 | 어디에 남나 |
|---|---|
| ①②⑤ | **이슈·PR·CI 로그** — 이미 남는다. 추가 조치 없음 |
| ③ⓐⓑ | **회부를 이슈 코멘트로 남긴다** — 결정을 구두로 하지 않고 해당 이슈에 *"선택지/근거/위험"* 을 적고 답을 단다. 그러면 분모(회부 건수)와 ⓑ(재요청)가 로그에 남는다. 🔵 **구현 확정 2026-08-29 — 결정당 이슈 하나**(`decision` 라벨). 규정이 *"**해당 이슈**에"* 라 했지 *"기존 작업 이슈에"* 라 하지 않았다 — **결정 자체가 이슈면 그게 해당 이슈**이고 답·재요청이 같은 스레드의 코멘트로 붙는다. `tools/check_decision_referrals.py` 가 센다 |
| ③ⓒ · ④ | ⚠️ **자기보고를 피할 수 없다.** *"그때 뭘 승인한 거지"* 와 *"뭘 만들려던 거지"* 는 사건이 아니라 **상태**다. 최소 완화: 발생 즉시 해당 이슈에 한 줄 코멘트를 남긴다(사후 회고 금지) |
| ⑥ | **지표 없음** — 미설계(`GAPS` R5-2) |

### 🆕 배포 축 — **사전 등록 (2026-08-30)**

목적 한 줄이 [rev8](01-what-i-want.md) 에서 늘었다 — *"그 방식을 **남이 설치해서 쓸 수 있게 포장**하는 것."*
**목적이 늘면 지표도 늘어야 한다.** 🔴 **관측이 시작되기 전에 박는다** — 위 규율이 그것이다.

⚠️ **왜 별도 축인가**: 위 ①~⑥은 전부 ***"내가 굴린다"*** 를 잰다. 2026-08-29 하루에
**이 축에서만 보이는 결함이 셋** 나왔는데(의존성 해석 · 버전 미갱신 · 커맨드 노출)
**나 혼자 쓰면 하나도 안 걸렸을 것**이다. 잴 눈이 따로 필요하다.

| 지표 | 무엇을 세나 | 어디에 남나 |
|---|---|---|
| **ⓓ 설치가 한 번에 서나** | `claude plugin install` **한 줄** 뒤에 `Status: ✔ enabled` 인가. 🔴 **의존성까지 포함**해서 센다 | **설치 로그**(`claude plugin list`) — 첫 실측 2026-08-30: **1차 실패 · 수정 후 성공** |
| **ⓔ 첫 명령에 도달하나** | 설치한 사람이 **다음 세션에서 `/kickoff` 이나 `/floor-check` 을 실제로 쓰나** | 그 저장소의 **이슈**(kickoff 이 남긴다) · 없으면 자기보고 |
| **ⓕ 판이 식별되나** | 문제가 생겼을 때 **"어느 판인가"** 에 답이 있나 — `plugin.json` 과 마켓 항목의 `version` 이 **일치하고 올라가는가** | `claude plugin list` 의 `Version` · `claude plugin tag` 가 불일치를 거부한다 |

🔴 **셋 다 *남* 이 있어야 진짜로 재진다.** 소유자 혼자 재면 ⓓ는 캐시가 가리고, ⓔ는 자기가 만든 것이라
안 잊고, ⓕ는 방금 짰으니 안다. **그래서 이 축의 관측 시작 조건은 *첫 외부 설치자* 다.**

⚠️ **지금은 n=1(소유자)이고 그것도 실패→수정이었다.** 판정하지 않는다 — **계기만 달아둔다.**

> ### 🔵 2026-08-29 — ③ 의 수단을 *결정당 이슈* 로 확정했다. **이건 완화가 아니라 강화다**
>
> 🔴 **실측이 먼저다**: 사전등록된 곳(이슈 코멘트)에 회부가 **0건**이었다. 오늘까지의 회부는
> **대화 · PR 본문 18건 · `GAPS` 대장**에 흩어져 있었다 — *수단은 적어뒀는데 아무것도 그걸
> 발화시키지 않는* 상태였고, 그게 이 저장소가 반복해 고쳐온 결함의 형태다.
>
> **수단을 바꿀 때의 판정은 *"수단이 달라졌는가"* 가 아니라 *"기준이 느슨해지는가"* 다** —
> §판정 기준이 *"결과를 보고 기준을 옮기지 않는다"* 로 시작하기 때문이다. 네 축 전부 **더 잡히는** 쪽이다:
>
> | | 코멘트 → 결정당 이슈 |
> |---|---|
> | **분모** | 라벨로 세므로 **더 많이·더 잘 보인다** |
> | **ⓑ 재요청** | 같은 스레드 — **동일** |
> | **ⓒ *"그때 뭘 승인한 거지"*** | 스레드가 통째로 남아 **찾기 쉬워진다** |
> | **작업량** | 코멘트 하나보다 이슈 하나가 **더 든다** |
>
> ⚠️ **수단을 정해도 자동으로 안 남는다.** 실제로 바뀌어야 하는 건 *"결정을 물을 때 먼저 그 자리에
> 적고 링크를 준다"* 는 **행동**이고, `check_decision_referrals.py` 가 그게 일어나는지 센다.
> 첫 회부는 [#141](https://github.com/coolbress/standards/issues/141)·[#142](https://github.com/coolbress/standards/issues/142) 다.
>
> **🔄 개정 2026-08-29 (같은 날)** — 시중·코퍼스를 확인해 셋을 더했다. ADR 은 불변이므로 #141 을 고치지 않고 **이어서 적는다**:
> ① **종류를 셋으로 가른다**(`decision:approval`·`:input`·`:escalation` — HITL 분류) ·
> ② **묻지 말아야 할 것**을 [`06`](06-how-we-work.md) 에 적었다(과다 회부 → *rubber-stamping* 이 실패 모드다) ·
> ③ **닫힌 회부는 `direction/`·`audit/` 에 인용돼야 한다** — RFC 는 이슈에 살아도 되지만 **결정은 커밋된다.**
> ⬜ **과다 회부 임계는 아직 안 만든다** — `R5-2` 의 θ 와 같은 이유로 **건강한 분포에서 재야** 하고, 3건으로는 분포가 없다.

⚠️ **따라서 *"요구 6개 전부 분모 있는 지표"* 는 과대 주장이었다.** ⑥은 지표가 없고 ③ⓒ·④는 자기보고다.
그 한계를 지우지 않고 적는다 — 확증시험이 자기에게 불리한 결과를 그대로 적었던 것과 같은 규율이다.

| 요구 | 지표 (분모 있는 것) | 실패 판정 |
|---|---|---|
| **① 팀처럼** | 머지된 PR 중 **CI 초록 상태로 머지된 비율** · 벽 우회 시도 횟수 | 우회가 1회라도 성공하면 실패 |
| **② 기획** | `/kickoff`를 거친 이슈 / 전체 이슈 · **AC가 검사에 매핑된 비율** | 매핑률 50% 미만 |
| **③ 결정·판독** | **회부된 결정 건수**(분모) 중 ⓐ 내가 되묻지 않고 판단한 비율 ⓑ *"쉽게 다시 설명해달라"* 재요청 횟수 ⓒ 나중에 *"그때 뭘 승인한 거지"* 가 발생한 건수 | ⓑ가 주당 3회 이상이면 전역 규칙 실패 · ⓒ가 1회라도 발생하면 회부 형식 실패 |
| **④ 맥락** | 세션 시작 시 *"뭘 만들려던 거지"* 발생 횟수 (주당) | 2주차에도 주 1회 이상 |
| **⑤ 오케스트레이션** | 위임 건수 · 위임 결과를 **그대로 채택한 비율** | 미착수라 판정 없음 |
| **⑥ 전략 전환** | 막다른 길 신호 발생 시 **감지까지 걸린 시간** | 미설계 (`audit/GAPS` R5-2) |

**요구 ③의 지표가 왜 이 모양인가**: 이 요구를 채우는 수단(만들 것 4·8)은 **전부 협조 기반**이다.
확증시험은 협조 기반 회부가 실사용에서 무너지는 것을 이미 보였다 — 승인 피로(*"창 떴는데 안 읽고 눌렀다"*)와
판독 실패는 **벽이 아니라 사람 쪽에서** 났다. 그러므로 *"우회 동기가 없으니 괜찮다"*(원칙 03)는
**논증되지 않은 건너뜀**이고, 위 ⓐⓑⓒ가 그 건너뜀을 측정한다. → `audit/GAPS` **R5-3**.
