# “현업급 산출물” 판정 기준 — goppi-final 설계 결정

> 상태: **채택된 프로젝트 기준** · 2026-08-02  
> 근거와 결정의 경계: SWEBOK·ISO·활성 corpus는 품질과 생명주기 범위를 제공하지만 “이 표를
> 통과하면 모든 제품이 현업급”이라는 보편 표준은 없다. 아래 등급·게이트는 goppi가 검증 가능한
> 완료 정의를 만들기 위해 채택한 synthesis다.

## 판정 원칙

“현업급”은 파일 수나 도구 목록이 아니라 **주장한 결과를 실행하고, 검증하고, 안전하게 전달하며,
실패에서 회복할 수 있는 상태**다. 모든 프로젝트가 최고 등급일 필요는 없다. 노출·데이터·금전·복구
비용·사용자 의존도가 올라갈 때 필요한 등급도 올라간다.

이 rubric은 산출물의 준비 상태를 판정하지만, goppi의 존재 가치 전체를 대신하지 않는다. 대상 사용자가
이 판정을 근거 없이 믿었는지, 증거를 구분했는지, 잘못된 agent 조언을 거절하거나 안전하게 위임했는지는
`goppi-worth-hypothesis.md`의 trustworthy-completion 평가에서 별도로 측정한다.

| 등급 | 뜻 | 허용되는 주장 |
|---|---|---|
| L0 Prototype | 아이디어와 핵심 경로를 시험함 | “탐색 가능한 시제품” |
| L1 Delivery-ready | 지정된 환경에서 재현·검증·인계 가능 | “다른 사람이 받아 실행 가능한 결과” |
| L2 Public-service-ready | 외부 사용과 운영 실패를 견딜 통제가 있음 | “사용자에게 공개·운영 가능한 결과” |
| L3 Consequential/regulated | 높은 피해·규제·금전 위험에 독립 검토와 감사 증거가 있음 | 해당 통제의 책임자가 승인한 범위의 주장만 |

L0를 L2처럼 소개하면 실패다. L1은 자동으로 L2가 되지 않는다. L3는 goppi 단독 판단으로 승인하지
않으며, 해당 분야의 책임자와 규제·조직 기준이 필요하다.

## 공통 8개 판정면

| 판정면 | 최소 증거 | L2에서 추가되는 것 |
|---|---|---|
| 실행 가능 | 깨끗한 환경의 실행 절차 또는 실행 로그 | 배포 환경의 health/readiness 확인 |
| 요구 추적 | 사용자 결과 → 수용 기준 → 검증 결과 연결 | 운영·보안·데이터 요구까지 추적 |
| 검증 | 실제 핵심 주장에 맞는 실행 가능한 검사 | 실패 경로, 통합·회귀, 위험 기반 검사 |
| 보안·개인정보 | 위협·민감정보·권한의 적용 여부와 disposition | 최소권한, secret 격리, abuse/privacy 검사 |
| 배포·릴리스 | 버전과 되돌릴 수 있는 전달 절차 | 단계적 배포, 변경 통제, 공급망 증거 |
| 관측 가능 | 실패를 알아차릴 방법 | 구조화 로그·메트릭·알림과 소유자 |
| 복구 가능 | 손실 시 복구/재생성 경로 | 백업·rollback을 실제로 시험한 증거 |
| 인계 가능 | 목적·실행·검증·알려진 한계 | 평문 운영절차, 책임 경계, incident 경로 |

각 면은 `PASS`, `NOT-APPLICABLE(reason)`, `FAIL`, `UNVERIFIED` 중 하나다. `UNVERIFIED`를 PASS로
바꾸는 설명문은 허용하지 않는다.

## Assurance overlay: 절차가 아니라 claim과 증거를 판정한다

각 `PASS`는 최소한 다음 5필드를 가져야 한다.

| 필드 | 질문 |
|---|---|
| Claim | 정확히 무엇이 됐다고 주장하는가? |
| Scope/condition | 어느 환경·버전·위험 범위에서만 맞는가? |
| Evidence | 어떤 실제 실행·관찰·검토 결과가 뒷받침하는가? |
| Residual unknown | 무엇은 검사하지 않았거나 아직 모르는가? |
| Recovery | 틀렸을 때 어떻게 감지·중단·되돌리는가? |

문서, issue, branch, PR, review, CI가 존재한다는 사실만으로 어느 면도 `PASS`가 되지 않는다. 예를 들어
“PR을 만들었다”는 process trace이고, “독립 검토가 acceptance criterion X의 결함을 발견·수정했고
재실행 결과 Y가 통과했다”가 claim-linked evidence다. 특정 절차가 증거·결정·위험 억제·복구에 기여하지
않으면 goppi 기본값에서 제거하거나 필요한 위험군으로 좁힌다.

## 아키타입별 추가 게이트

| 아키타입 | L1 핵심 | L2/공개 시 추가 게이트 |
|---|---|---|
| library/package | 지원 버전, API 계약, 소비자 설치 검사 | 호환성·deprecation·provenance·release 복구 |
| CLI/local tool | exit code, 오류·dry-run, 데이터 위치 | 설치/업데이트/rollback, credential·filesystem 경계 |
| web/mobile UI | 주요 사용자 흐름, 접근성 기본 검사 | auth/session, 개인정보, 브라우저/기기 호환, 정책 고지 |
| backend/API | 계약·migration·통합 검사 | rate limit, authz, zero/low-loss rollback, SLO·incident |
| data/ML | 데이터·모델 provenance, 재현 가능한 평가 | drift/quality monitor, rollback, 오용·편향 경계 |
| AI harness | 결과 기반 eval, 권한·도구 경계 | prompt injection, credential/egress/prod 격리, audit/recovery |

## 비개발자에게 보고하는 형식

승인 요청은 다음 다섯 문장을 채우지 못하면 informed-decision 증거로 세지 않는다.

1. **하려는 일:** 기술 용어 없이 사용자의 결과로 설명한다.
2. **일어날 수 있는 피해:** 대상·범위·최악의 결과를 구체화한다.
3. **막아 둔 것:** 모델의 약속이 아니라 실제 권한·격리·검사를 말한다.
4. **확인할 증거:** 실행할 검사와 사용자가 보게 될 결과를 말한다.
5. **되돌리는 법과 남은 미확인:** 복구 경로와 아직 모르는 것을 함께 말한다.

`승인하시겠습니까?`만 반복하거나 코드 diff만 보여주는 것은 informed-decision 증거가 아니다. 다만
다섯 문장을 보여 주거나 사용자가 그대로 되풀이했다는 사실만으로 이해를 인정하지도 않는다. 사용자
시험에서는 새 사례의 선택, 잘못된 agent 조언의 거절/escalation, 실제 recovery 동작으로 이해를 함께
확인한다. 사용자가 결과·피해·복구를 구분하지 못하면 더 강한 시스템 통제를 적용하거나 작업을 중단한다.

## 운영자 없는 운영과 마지막 마일

솔로 소유 프로젝트에서 “24시간 on-call 팀”을 흉내 내지 않는다. 대신 공개 서비스라면 최소한
다음을 갖춰야 한다: managed service로 줄인 운영면, 자동 백업, 오류 수집, 비용 상한/알림, 사용자가
실행 가능한 평문 runbook, 서비스 중지 또는 rollback 경로. 이 최소 세트의 효과는 아키타입별 실증이
더 필요하므로 roadmap의 R1-9로 남긴다.

도메인·호스팅·결제·개인정보 고지·스토어 심사 등 마지막 마일은 범용 floor가 아니다. 주 아키타입이
정해질 때 해당 출시 체크리스트를 활성화하고, 결제·개인정보·외부 출시는 Governed 게이트로 올린다.

## 검증 표면

- 모든 기획 spec은 목표 L등급과 8개 판정면의 disposition을 기록한다.
- 완료 보고서는 최소 한 개의 실제 결과 검증 명령과 알려진 한계를 포함한다.
- L2 이상은 seeded failure로 탐지→알림→복구 경로를 한 번 실행한다.
- 사용자 테스트에서 참가자가 결과·증거·남은 위험·복구를 자기 말로 구분하고, 새 decision scenario에서
  올바르게 승인·거절·escalate하는지 확인한다.
