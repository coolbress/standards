# 종합: 현업 소프트웨어 프로젝트는 어떻게 진행되는가 (초간단판)

> 4개 리서치 파일(01~04)의 종합. 상세 근거와 출처는 각 파일 참조.
> 01: SDLC 전체 흐름 · 02: 일상 엔지니어링 실무 · 03: 기획/요구사항 · 04: 솔로/AI-보조 개발

## 한 문장 요약

**현업 개발은 "큰 계획을 완성하고 순서대로 실행"하는 게 아니라, "문제를 좁히고 → 얇은 조각 하나를 끝까지 만들어 → 검증하고 → 배우고 → 다음 조각"을 반복하는 짧은 루프이며, 성과를 가르는 것은 방법론 이름이 아니라 [작은 배치 · 잦은 통합 · 자동 검증]이라는 세 가지 행동이다.**

## 표준 루프 (기능 하나당 도는 사이클)

```
① 문제 심문      "진짜 뭐가 안 되고 있죠?" — 해결책 말고 문제부터.
                 과거의 구체적 행동을 묻는다 (Mom Test).
② 스펙 (얇게)    문제 한 문단 + 성공 기준 + non-goals + 인수기준 체크리스트.
                 시간 예산(appetite)을 먼저 정하고 그 안에 들어갈 해법을 설계.
③ 설계 (조건부)  되돌리기 어렵거나 트레이드오프가 클 때만 짧은 설계 문서.
                 내린 결정은 ADR 몇 줄로 저장소에 기록 (기각한 대안 포함).
④ 구현           첫 조각은 항상 walking skeleton (핵심 시나리오 하나가
                 end-to-end로 도는 가장 얇은 수직 슬라이스).
                 이후에도 수직 슬라이스만 — "DB 전부→API 전부→UI 전부"는 금지.
                 변경은 작게 (~수백 줄), 브랜치는 짧게 (시간~하루), 매일 통합.
⑤ 검증           테스트는 변경과 같은 커밋에 함께. 빠른 소형 테스트 다수 +
                 E2E 극소수 (80/15/5). CI 녹색 + 리뷰 통과가 "done"의 최소선.
⑥ 릴리스         deploy(코드 반영)와 release(사용자 노출)를 분리.
                 feature flag, canary 등으로 점진 노출.
⑦ 운영→학습      에러·사용 데이터·인시던트가 ①로 다시 흘러들어 루프를 닫는다.
```

## 하중을 받는 것 vs 형식(ceremony)

| Load-bearing (지키면 성과가 달라짐) | Ceremony (조직 조율용 — 작은 규모에선 버림) |
|---|---|
| 문제 진술 + 성공 기준 + non-goals | 풀 PRD, 페르소나 문서, 승인 워크플로 |
| 인수 기준의 **테스트 가능성** | Given/When/Then 형식 그 자체 |
| walking skeleton 먼저, 수직 슬라이스 | 간트 차트, 상세 산정 문서 |
| 시간 고정 + 범위 가변 (appetite + scope hammering) | 스토리 포인트, 플래닝 포커, 번다운 |
| 작은 PR + 빠른 리뷰 (1영업일 내, ≤400줄) | 다중 필수 승인자, 형식적 체크리스트 |
| 자기검증 CI (테스트 포함, ~10분, 깨지면 즉시 수리) | 커버리지 배지, 100% 커버리지 |
| 테스트가 변경과 함께 오는 것 | test-first 순서의 의식적 강제 |
| 커밋 첫 줄 요약 + "왜" 본문 | 자동화가 소비하지 않는 Conventional Commits |
| ADR (결정 + 기각한 대안, 저장소 안에) | 위원회식 RFC 리뷰 |
| 브랜치 수명 단축 + 매일 통합이라는 **행동** | 브랜치 모델 명칭·다이어그램 준수 |

## 실패는 어디서 오는가 (증거 기반)

1. **불명확한 요구사항 / 사용자 미참여** — 30년간 부동의 1위 (CHAOS).
2. **크기** — 소형 프로젝트 성공률 ~90% vs 대형 <10%. 처방은 "쪼개라".
3. **스코프 크리프** — 방어책은 변경 금지가 아니라 시간 상한 + circuit breaker.
4. **빅뱅 통합** — 처방은 walking skeleton + 항상 동작 상태 유지.
5. **검증 부재/지연** — AI 시대에 더 심해짐: 생성은 싸졌고 검증이 병목 (DORA 2024/25).

## 솔로 + AI 에이전트 규모로 접으면

- **남는 것**: 버전 관리, CI, 테스트, 짧은 스펙, 독립 리뷰 — 전부 "artifact가 스스로 말하는" 검증 표면. 에이전트가 그 표면을 향해 일할 수 있어서 오히려 중요도가 올라간다.
- **죽는 것**: 스탠드업, 스프린트, 추정 — 전부 "사람이 사람에게 말하는" 조율 장치.
- **비개발자 사용자가 위임할 수 없는 유일한 역할은 PM**: 문제 정의, 시간 예산 결정, 수용 판정. 나머지 역할(설계·구현·QA·운영)의 책임은 하네스가 구조적으로 짊어져야 한다.
- **자연어 지시는 게이트가 아니다** (Replit DB 삭제 사건) — 환경 분리·권한만이 게이트다.
- **하네스는 얇아진다**: 절차 지시("이 순서로 해라")부터 만료되고, 끝까지 남는 것은 검증 표면(테스트·CI·권한 게이트)과 컨텍스트 위생이다.

## 하네스 설계로의 한 줄 결론

**"어떻게 만들지 지시하기"에서 "무엇이 완료인지 정의하고, 그것을 기계가 확인 가능하게 만들기"로 무게중심을 옮겨라** — 솔로 문헌, SDD 비판, Anthropic 가이드, bitter lesson이 전부 같은 방향을 가리키며, 모델이 강해질수록 가치가 커지는 유일한 투자다.
